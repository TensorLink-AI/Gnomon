# Continuous-origin development preparation

This is a prospective preparation amendment, before exporting new task files or
fitting any model on them. It does not change or interrupt checkpoint-v3, promote
a candidate, open a final holdout, or establish the 20% objective.

The current ML development schedule uses rounds 0,1,2,3,22,23,24,25. Therefore
its first “later” decision has only four earlier decisions, and no session has
more than seven. Calendar lateness is not accumulated experience. This schedule
can test execution and limited reuse, but not a ten-origin learning/cold-start
hypothesis. Retain its results and label that limitation explicitly.

Prepare all rounds 0 through 25, in chronological order, on the same four
development series. Use the original first origin, a fixed 14-day stride/horizon,
730 observed history values, and the same supplied promotion/calendar covariates.
Do not select dates, configurations, items or stores based on forecast errors or
hindsight gains. Each decision at round k can then see k mature earlier horizons.
No old candidate scores, cards, rankings, predictions or explanations are inputs.

Source: the frozen v1 host bundle with SHA-256
836e05229535f144acab46e94d48fb0fbddf2acc9b9bf4696369f5149efb9ec9.
Its overlapping history and target arrays already cover the entire required
development interval. Reconstruct by timestamp identity; reject inconsistent
overlaps, missing observations, changed metadata or nonfinite/negative sales.
Never interpolate or resolve a conflict. Reproduce all 32 existing task records
exactly after removing non-task metadata. Export only request, actual, origin,
outcome_recorded_at, future_timestamps, series_id and round, to host-only storage.

Keep the existing synthetic availability convention: outcomes become eligible
after horizon close; supplied future promotion/calendar variables are treated as
known inputs. Their real publication vintages are not established. The agent
receives only its current history, provided future covariates and mature prior
outcomes through the same common lab preparation. Perturbing later sales must
not change an earlier request; changing arrived observations must affect later
history. Candidate-card/score metadata must have no effect on exported tasks.

This command performs no provider fit, inference, scoring or ledger mutation.
It accepts only the pinned development source and refuses an existing output
directory. Test source consistency, temporal perturbations and metadata exclusion
before export. Record hashes and reproduce the export independently.

Any subsequent agent run requires its own frozen protocol after the current
pilot/development result is assessed. Keep equal capabilities, raw evidence,
numerical/API/correction budgets and completion handling; the ledger treatment
organizes accumulated evidence. Include the matched frozen 1.1.9 comparator
before a final-goal claim. Define its dynamic-configuration evidence adapter
before inference, rather than penalizing it with unmatched configuration pools.

All 104 prepared cases are development data. Reserved M5 series remain unopened.
This amendment does not call a reused series holdout, lower the 20% RMSLE bar,
substitute workflow completion for accuracy, or alter final uncertainty rules.
