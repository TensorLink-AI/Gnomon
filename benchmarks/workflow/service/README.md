# Isolated lean/full services

The shared driver can now expose real Gnomon MCP services alongside the same
[ordinary software](../software/README.md), using separate owned containers.
This is not a paid experiment, new Gnomon library adapter or production deployment.

## Build and configure

Build the current wheel, then the service image with narrowly scoped input contexts:

```bash
python -m build --wheel --outdir service-wheel
docker build --pull=false --build-context ordinary-lock=benchmarks/workflow/software \
  --build-context core-wheel=service-wheel \
  -t gnomon-bench-service:local benchmarks/workflow/service
docker image inspect gnomon-bench-service:local --format '{{.Id}}'
```

This uses the same pinned base/hashed dependency lock as ordinary software and
installs only the explicit Gnomon wheel, with no dependency resolution at runtime.
The main context admits only Dockerfile; named contexts provide only the dependency
lock and wheel. No case corpus, checkout mount or host credentials are needed.
Include service Dockerfile and the ordinary lock/build inputs in `driver_files`.
If normal Docker configuration is read-only, use a new private `--config` directory.

Set the lean and full entries in the common driver provider JSON to these shapes,
replacing both deliberately invalid image placeholders with actual local image IDs:

```json
{
  "lean": {
    "factory": "benchmarks.workflow.service_backend:lean",
    "options": {
      "software_image": "sha256:ACTUAL_ORDINARY_IMAGE_ID",
      "service_image": "sha256:ACTUAL_SERVICE_IMAGE_ID",
      "docker_host": "unix:///var/run/docker.sock"
    }
  },
  "full": {
    "factory": "benchmarks.workflow.service_backend:full",
    "options": {
      "software_image": "sha256:ACTUAL_ORDINARY_IMAGE_ID",
      "service_image": "sha256:ACTUAL_SERVICE_IMAGE_ID",
      "docker_host": "unix:///var/run/docker.sock"
    }
  }
}
```

Startup verifies the service's entire installed Gnomon package against checkout
file bytes, excluding generated bytecode. Python, distribution versions and
public-input hashes are recorded; ordinary/service versions must agree except
for the service's added Gnomon distribution. A stale wheel is rejected, not silently
called the current checkout. This does not independently attest every third-party
dependency's source, remote weights or the operator's honesty.

## Contracts and state

- Ordinary exposes `python` in its software-only container. Lean adds the actual
  current MCP service:6 Gnomon tools by default,7 tools total.
- Full uses the same execution contract with ledger and temporal tools enabled:
  9 Gnomon tools,10 total. Both arms require an explicit provider; neither performs
  hidden model selection. Arguments are not repaired and answers are not filled
  from tool output. This compares feature availability, not just tool count.
- Lean optionally accepts `execution_options: {"ledger": true, "temporal": true}`
  in its options, adding route/ledger/temporal discovery (10 tools including Python).
  These are explicit pinned startup differences. Full enables both by default;
  overrides must be recorded and change the experiment's interpretation.
- Service operator configuration is a root-owned read-only file; agent outcome writes
  remain disabled. Forecasts can be saved/retrieved/scored through the ledger,
  but actuals must come from an operator-controlled path. Tests use a synthetic
  operator append to verify preserved forecasts and scoring, not agent-written
  actuals or a completed staged experiment. No live provider config is injected.
- MCP process state persists across calls, including data references and optional
  ledger state. Initialize/initialized/list/call use the actual stdio server.
  Byte/deadline/JSON/request-ID failures close the service; ordinary MCP tool-error
  results remain available for agent repair. No automatic service retry occurs.

Public `available_at_cutoff.files` can map up to32 simple filenames to UTF-8 text.
The exact same files are placed under `/tmp/data` in both containers; total public
input remains byte-bounded. No path traversal, absolute path or host file import
is accepted. These are supplied task files, not a host conversion of observations
or rewritten tool arguments. The copies are independent: Python-generated files
are not automatically shared with the service, and vice versa. No future-stage
observations are preloaded. Multi-phase episodes reveal updates only after the
prior phase's answer; see the experiment protocol.

## Limits and checks

Both containers inherit the software backend's no-network/no-host-mount/read-only/
non-root-agent limits and protected lifetime timer. Cleanup always attempts both
components, verifies exact ownership and never prunes other containers. A stopped
create/start orphan remains possible; kernel/daemon failures are not disguised as
successful cleanup. This is not VM isolation or hostile-code certification.

Lean/full use **two independent container budgets**, while ordinary uses one.
Extra service capacity/startup is recorded, not claimed equal total compute. Model
round/token/tool limits still apply across the combined inventory. Local service
charges exclude infrastructure; no lower-cost conclusion follows without measured
complete accounting and disclosed resource differences.

```bash
GNOMON_TEST_SOFTWARE_IMAGE=$(docker image inspect gnomon-bench-software:local --format '{{.Id}}')
GNOMON_TEST_SERVICE_IMAGE=$(docker image inspect gnomon-bench-service:local --format '{{.Id}}')
export GNOMON_TEST_SOFTWARE_IMAGE GNOMON_TEST_SERVICE_IMAGE
python -m pytest -q benchmarks/tests/test_software_backend.py benchmarks/tests/test_service_backend.py
```

The dedicated CI job explicitly builds both images and runs these checks. Local
tests cover lean and ledger-enabled forecasts, exact discovery/contracts, persistent
data references, tool-error recovery, source mismatch, lifecycle cleanup and the
optional ledger's saved prediction/actual-write permission/score path. No model
superiority or agent-quality claim is inferred from those checks. A suitable
corpus, genuine staged agent behavior, total spending controls and actual matched
agent runs are still required for production ablation credit.
