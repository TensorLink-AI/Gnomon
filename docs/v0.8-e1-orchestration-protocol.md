# v0.8 E1 economical and resilient orchestration protocol

Status: frozen after topology audit and corpus generation, before the fresh
baseline or production change.

## Diagnosed user boundary

On the retained v0.7 Q5 development shard, compiled Evidence already used the
minimum one Gnomon product call per case. It nevertheless spent nine final
agent requests plus three compiler requests cold and ten final-agent requests
warm. Every case used one model turn to issue a host-known, host-bound
`gnomon_forecast` call and a second turn to synthesize the result; repair-only
submission turns added one cold and two warm requests. Cold prompt usage was
58,275 tokens total and warm final-agent usage was 63,342 prompt tokens.

This is not a forecasting-engine defect. It is an integration-boundary defect:
when a trusted host has already compiled a typed forecast intent and bound the
validated dataset, asking a model to repeat the deterministic tool selection
adds no semantic authority. Separately, the engine exposes every response
obligation but does not provide one compact canonical synthesis contract, so a
model can omit a source or authority statement and require repair.

## Frozen arms

Both arms use ContextBench `run_surfaces`, Evidence,
`deepseek-v4-flash-0731` through Engy, compiled routing, engine baseline,
temperature zero, reasoning effort none, `jobs=1`, 180-second request timeout,
120-second MCP timeout, two provider retries, and two bounded row-level
infrastructure retries. Each arm runs cold into an empty compiler-receipt
directory and warm against exactly those immutable receipts.

Baseline is the current two-turn MCP topology: the model issues the forced
host-bound tool call, receives the result, and submits its synthesis.

Candidate has two inseparable general components:

1. Gnomon's publication supplies a bounded deterministic
   `agent_response_contract`, copied only from already-published disposition,
   relationship, source, uncertainty, primary-authority, and automation facts.
2. A host that has a typed, validated, fully bound forecast intent may execute
   the single advertised Gnomon tool before the final agent call, then offer
   only `submit_answer`. The result and contract remain in the model input;
   model synthesis remains measured. Uncompiled or ambiguous requests retain
   the ordinary agent-driven MCP loop.

The candidate may not change forecast numbers, context compilation or
admission, scenarios, sources, support, calibration, automation, tool schema,
or submission validation. The host-preexecution decision depends only on a
typed bound intent, never corpus or benchmark identity.

## Frozen measurements and gates

Report compiler, product-tool, final-agent, transport, repair, cache, prompt,
completion, response-byte, and stage-latency results separately. Cached
receipt metadata is not current-run cost.

- 4/4 completion in every lane; zero leakage; exact forecast, artifact,
  disposition, source, gate, relationship, primary, interval, and automation
  parity between arms.
- Exact preservation of every applicable source reference, rejection code,
  conditional consequence, `no_distinct_numeric_path`, primary-preservation
  statement, interval limit, and automation limit in final agent output.
- Exactly one Gnomon product call per case and zero duplicate product actions.
- At least 25% fewer final-agent requests and prompt tokens in both cold and
  warm development. Warm end-to-end requests and prompt tokens also fall at
  least 25%; cold compiler work may not increase.
- Zero repair-only turns caused by response-contract facts.
- p95 stage latency may not regress by more than 10% unless the absolute
  difference is under one second.
- Missing, invalid, ambiguous, or unbound intent fails back to the ordinary
  agent-driven loop. Host execution failure is disclosed and never followed
  by an automatic duplicate action.
- Deterministic fault injection proves only an unfinished row reruns,
  completed rows remain byte-identical, attempts remain append-only, and
  resumed usage counts only new calls.
- Existing ContextCacheBench product parity and MCP discoverability remain
  exact.

One candidate revision is allowed on development. A green exact candidate must
repeat the gates on untouched confirmation, pass focused tests, actual response
inspection, and the TSFM-isolated full suite. Otherwise retain a documented
no-build and continue to F1.
