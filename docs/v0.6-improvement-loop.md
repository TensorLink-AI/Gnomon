# Gnomon v0.6 product-improvement loop

Status: active development protocol. The machine-readable current state lives
in the latest `results/benchmark-releases/*-v06-loop-*/checkpoint.json`.

## Objective

Improve Gnomon as a forecasting execution boundary for agents while making
every accepted change visibly useful to either the agent operating it or the
human acting on its answer. Work continues one bounded experiment at a time
until every registered priority either clears its completion gate or reaches a
predeclared, evidence-backed no-build decision.

The loop does not optimize runtime behavior to benchmark names, task IDs,
labels, answer choices, or hidden futures. A benchmark can reveal a general
defect; it cannot become an input to the fix.

## North-star user outcomes

An accepted improvement must advance at least one outcome without materially
regressing the others:

- **Agent correctness:** the agent preserves Gnomon's numbers, typed
  relationships, support tiers, warnings, and abstentions in its final answer.
- **Human decision quality:** the answer makes the relevant action, risk,
  uncertainty, evidence, and alternatives understandable and later scoreable.
- **Forecast skill:** published paths and probabilities improve over registered
  baselines on honestly available data.
- **Answer yield:** more appropriate questions receive useful supported output,
  without converting uncertainty into invented precision.
- **Operational reliability:** bounded calls complete predictably, resume after
  interruption, disclose fallback behavior, and remain within stated cost and
  latency budgets.

Passing tests is necessary but is not itself a user outcome.

## One iteration

Only one priority may be active at a time.

1. **Choose.** Re-rank unfinished priorities using observed user harm,
   dependency order, expected general usefulness, evidence strength, and the
   cost and risk of learning more.
2. **State the user hypothesis.** Name the agent or human experience that
   should improve and the behavior that must not regress.
3. **Freeze the gate.** Record the corpus, arms, denominators, metrics, seeds,
   retry and timeout policy, minimum effect or non-inferiority boundary, and
   kill criterion before implementation.
4. **Baseline.** Run the smallest representative shard that can reproduce the
   gap. Retain raw rows, completeness, configuration, commit, dirty state, and
   hashes.
5. **Change one boundary.** Implement the smallest general production-useful
   change. Do not combine unrelated estimator, prompt, interface, and policy
   changes in one experiment.
6. **Verify locally.** Add contract and property tests, then run the focused
   suite. Verify negative paths and invariant preservation, not only the new
   happy path.
7. **Validate independently.** Run a matched treatment/control benchmark that
   was not used as runtime input. Use small shards, `jobs=1` for API-driven
   agent work, bounded retries and timeouts, and resumable output directories.
8. **Inspect actual answers.** Aggregate scores do not replace reading the
   tool artifacts and final agent responses. Separate engine-contract
   completeness from agent preservation.
9. **Decide.** Mark the iteration `promote`, `revise`, or `reject`. Promotion
   requires the frozen user gate and all safety invariants. A rejected
   experiment remains documented and disabled or removed.
10. **Checkpoint and compact.** Update the checkpoint with evidence paths,
    results, decision, remaining risks, exact next command, and the next active
    priority. Commit only intended files, then begin the next iteration from
    the checkpoint rather than conversational memory.

## Validation layers

Every priority uses the layers that apply, and Priority P1 makes them a common
release scorecard:

1. **Output:** forecast error, calibration or coverage, answer yield, decision
   value or regret, and safety outcomes.
2. **Reasoning:** evidence sufficiency and necessity, temporal alignment,
   numeric/rationale consistency, caveat survival, and typed-relationship
   preservation.
3. **Topology:** completion, latency, calls, tokens or cost, retries, stability
   across seeds/models, and sensitivity to branch or stopping budgets.

Results from different layers are never collapsed into one accuracy number.

## Crash-safety and reproducibility

- API-driven benchmarks default to one worker. Locally hosted TSFM inference
  may use a GPU, but GPU availability does not justify higher API concurrency.
- Each paid or long-running runner must write rows incrementally, resume from
  completed case IDs, use bounded retries, and impose per-call and wall-clock
  timeouts.
- The first run is a smoke shard. Larger shards begin only after its artifacts
  and final answers pass manual inspection.
- Every checkpoint names the evaluated commit and dirty-tree state. Evidence
  produced by older code remains historical and cannot validate newer code.
- Existing committed work, benchmark artifacts, and all pre-existing untracked
  files are preserved. `docs/astrid-btc-agent-plan.md` is explicitly excluded
  from this loop and from its commits.

## Priority register and completion gates

| ID | Priority | User experience served | Completion gate |
| --- | --- | --- | --- |
| P1 | Three-layer release scorecard | Agents avoid silent upgrade regressions; humans can distinguish better numbers from better explanations or reliability. | A versioned, machine-readable scorecard validates output, reasoning, and topology evidence separately; missing denominators or provenance fail closed; tests and a retained smoke report pass. |
| P2 | Short-history forecast skill | Agents return more than a last-value path for new or sparse series; humans get useful early planning guidance with honest transfer disclosure. | A preregistered, independently matched evaluation shows material error improvement over the robust fallback, no safety regression, and stable results across named domains or records a no-build result for each candidate family. |
| P3 | Sourced contextual evidence | Agents can use plans, calendars, logs, and dated documents without inventing effects; humans can inspect what changed the answer. | Appropriate naturalistic tasks supply admissible evidence at the preregistered rate, extraction precision remains at its gate, and admitted context improves matched outcomes without leakage. |
| P4 | Covariate-aware and multivariate candidates | Agents submit related signals together; humans receive forecasts reflecting known drivers rather than isolated series. | At least one adapter proves its advertised protocol with contract tests and beats its identical-fold univariate baseline prospectively, or the adapter path reaches a documented no-build decision. |
| P5 | Outcome-adaptive champion/challenger routing | Agents reuse locally proven methods; humans see improvement over time with safe rollback. | Point-in-time shadow outcomes, minimum evidence, drift reset, non-automation safeguards, and rollback are contract-tested; prospective routing meets its registered skill and non-inferiority gates. |
| P6 | Joint multi-horizon uncertainty | Agents answer cumulative and any-step breach questions coherently; humans receive probabilities matching the decision they face. | Joint-event probabilities and trajectories pass coherence/property tests and improve registered calibration or decision scores without widening intervals beyond the frozen usefulness bound. |
| P7 | Hierarchical reconciliation | Agents stop emitting totals that disagree with components; humans can plan consistently across organizational levels. | Reconciled paths are exactly coherent and non-inferior at every registered hierarchy level, with a positive aggregate weighted-error result or a documented no-build decision. |
| P8 | Agent decision brief and preservation contract | Agents receive one compact answer they can quote correctly; humans see an action, risk, evidence, limits, and alternatives. | Matched boundary probes across registered agent models preserve critical typed facts and relationships at the frozen rate while improving or preserving task success, calls, and latency. |
| P9 | Value-of-information recovery | Agents know the next permitted action instead of retrying blindly; humans receive constructive requests rather than opaque refusals. | Recovery actions are ranked, executable, and causally tied to support blockers; matched tasks improve supported yield or reduce wasted calls without lowering admission precision. |
| P10 | Production inference reliability | Agents resume safely after failures; humans receive predictable, traceable answers within useful budgets. | Fault-injection and representative load tests meet frozen completion, p95 latency, cost, retry, resume, and no-silent-fallback gates. |

## Promotion rules shared by every priority

- Leakage and immutable-primary invariants remain exact gates.
- Engine completeness and final-agent preservation are scored separately.
- Missing, timed-out, or abstained rows remain in denominators under the
  preregistered policy.
- Improvements are reported with paired effects and uncertainty, not only
  aggregate means.
- A result on synthetic data is labelled synthetic and does not establish
  real-world superiority.
- No public accuracy claim changes until a complete retained run supports it.

## Reprioritization

The numeric order is a starting order, not permission to ignore new evidence.
A safety or correctness defect can pre-empt the active priority. Otherwise,
dependencies govern the sequence: P1 precedes all promotion claims; P3
precedes event pooling; outcome collection precedes automatic routing; and
reliable topology measurement precedes expanding branch or multi-agent work.

Every reordering is written to the checkpoint with its user-impact reason.
