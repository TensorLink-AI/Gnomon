# V0.6 P9 value-of-information recovery protocol

Status: frozen before production changes on 2026-08-30.

## User hypothesis and audit finding

When Gnomon cannot meet the requested evidence floor, an agent should receive
the smallest honest argument patch that can produce a useful next result in one
call. A human should see what will change, what will not, and whether new data
or judgment is required.

The current product has broad recovery coverage: every raised error code has
repair options, forecast support carries recovery actions, brief mode retains
them, and the reasoning boundary recommends the first authored action. The
general defect is executability. Real support actions contain only `code` and
prose. For example, a seven-step short-history refusal recommends horizon four,
but retrying only that field under the original `minimum_support=supported`
hits a second publication-floor refusal. The synthetic BoundaryBench fixture
uses `{tool, arguments}`, while real responses do not. Agents must parse prose,
guess which original arguments to retain, and may need avoidable retries.

## Bounded candidate

Keep every existing reason and recovery action byte-compatible, and add a
response-only `recovery_plan` projection. Each item contains:

- rank and recommended flag in the product-authored order;
- action code, exact source pointer, and description;
- execution mode: `tool`, `user_input`, `instruction`, or `unavailable`;
- tool plus an additive `argument_patch` only when Gnomon can specify both
  deterministically; otherwise `requires_user_input=true` and no guessed args;
- expected effect, evidence/authority limit, and whether a new external fact is
  required.

The reasoning envelope and error rejection point to the same first typed plan
item. Automatic support recoveries may be added only for:

- `lower_minimum_support`: retry `gnomon_forecast` at the exact achieved tier;
- `reduce_horizon`: retry at `max_supportable_horizon`; if the original floor
  can cause a second refusal, the explicit patch also permits `best_effort`,
  while promising only the tier actually earned;
- `retry_best_effort`: retry the same forecast with
  `minimum_support=best_effort`.

Other repair options remain visible but non-automatable until their missing
choice or external input is known. The projection cannot change canonical
numbers, evidence, support, artifacts, or automation eligibility.

## Frozen RecoveryBench

Run six deterministic current-head fixtures through the real public response
contract:

1. short history, horizon 1, requested `minimum_support=supported` (lower the
   floor to the exact achieved tier);
2. short history, horizon 7, requested `minimum_support=supported` (one-call
   compound horizon/floor recovery);
3. short history, horizon 7, default floor (reduce to a fully evaluated
   horizon);
4. missing input file (`check_path` requires external correction);
5. ambiguous frequency (`set_frequency` requires a caller choice);
6. malformed decision actions (`fix_actions` requires corrected input).

Baseline execution found one additional boundary defect in fixture 6: the MCP
schema describes the right action shape, and the CLI validates it, but a direct
public tool runner lets string items reach the decision macro and leaks an
`AttributeError`. The candidate may replace that one unhandled exception with
the existing typed `INVALID_ACTIONS` contract. Canonical immutability remains
exact for the other five cases; fixture 6 instead gates on typed-error contract
completion with the authored `fix_actions` repair. This is a benchmark-found
correction to a false baseline premise, not a change to the candidate target.

Manual inspection of the first successful compound retry found a second
general boundary contradiction: the recovered, usable forecast declared
`requires_follow_up=false` while `resolution.kind=recovery` because optional
evidence-improvement actions took precedence over task sufficiency. The
candidate may make a usable tier floor resolve `complete` while retaining its
optional `recovery_plan`; inconclusive/refused floors must still resolve to the
first recovery. This intentional boundary correction is allowed only where the
baseline fields contain that contradiction.

The same inspection also showed the inverse half of the defect in the original
refusals: their top-level response omitted `support`, so the boundary treated a
headline as a usable canonical answer and emitted `requires_follow_up=false`
despite `tier_floor=inconclusive`. The candidate must use the typed tier floor:
those two refusal fixtures change only to `requires_follow_up=true` and retain
their recovery resolution.

The short fixture is `tests/data/golden_short.csv`; use isolated output
directories, local statistical candidates, jobs=1, one retry, a 30-second case
timeout, atomic JSON rows, and resumable identity. For automatic candidates,
merge the advertised patch into the original call and execute it through the
real `gnomon_forecast` runner. Baseline is commit `a2e1b6e` before the typed
plan. No LLM is needed: the measured boundary is whether an agent receives an
executable call rather than prose it must reinterpret.

## Frozen gates

All six fixtures remain denominators.

- **Completion:** 6/6 baseline and 6/6 treatment responses complete.
- **Canonical immutability:** removing `recovery_plan` and its reasoning/
  rejection reference leaves all pre-existing response fields exactly equal.
- **Coverage:** every active blocker with authored recovery actions exposes the
  same actions in `recovery_plan`; no action is silently dropped.
- **One-call recovery:** all three automatic support fixtures carry exact tool
  patches and their first recommended automatic call produces forecast rows at
  an honestly labelled tier in one call. Baseline automatic one-call recovery
  is scored as unavailable when no exact patch exists, not guessed from prose.
- **No fake automation:** all three external-choice fixtures have
  `requires_user_input=true`, no executable argument patch, and retain their
  original repair descriptions.
- **Ranking:** the first plan item is recommended, ranks are unique and
  consecutive, and an executable no-new-data action precedes data collection
  when both address the active blocker.
- **Causal effect:** every automatic item names the blocker it addresses and
  the expected output change; it never promises a support upgrade, accuracy
  gain, or automation authority.
- **Traceability:** every item points to an existing recovery/repair field, and
  the reasoning/rejection resolution references an identical typed item.
- **Topology:** jobs=1, bounded timeout/retry, atomic resume, and complete
  denominators.

## Stop rules

Promote only if all gates pass and at least two of three support fixtures
improve from no exact one-call recovery at baseline to successful one-call
recovery. Do not add guessed paths for file locations, frequency, schema,
context, costs, or human policy choices. If deterministic patches cannot
recover honestly, retain the prose actions and record no-build rather than
teaching agents to weaken evidence silently.
