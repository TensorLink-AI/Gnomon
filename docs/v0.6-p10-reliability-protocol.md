# V0.6 P10 production inference reliability protocol

Status: frozen before production changes on 2026-08-30.

## User hypothesis and audit finding

Agents should be able to repeat or resume the same forecast without corrupting
its evidence, hanging, or receiving a transport failure. Humans should either
receive one complete integrity-sealed artifact or a typed/diagnosable failure;
a partial directory must never masquerade as a completed run.

The production surface already has strong pieces: content-addressed IDs,
integrity seals, directory-level atomic publication, first-write-wins reuse,
typed unexpected MCP failures, per-run TSFM timeout circuits, SQLite
transactions, and extensively tested benchmark resume identities. The audit
found one general concurrency risk. `write_artifact` and `write_json_artifact`
use one deterministic `.ID.tmp` directory. Two processes publishing the same
content ID can delete or write into each other's temporary tree before the
atomic rename. Atomic final publication does not make the construction phase
race-safe.

## Bounded candidate

Give every writer a unique hidden temporary directory under the requested
output parent. Seal and verify that private tree before publication. Publish by
an atomic no-overwrite rename. If another writer wins the same content ID,
verify the winner, remove only the losing writer's own tree, and return the
winner. A failed writer retains only its own uniquely named partial directory
for diagnosis and logs that path; no writer may delete another active writer's
work.

Do not add a daemon, distributed lock, automatic model fallback, background
retry, or new concurrency default. Do not change artifact IDs, artifact bytes,
support, forecast numbers, evidence, or automation authority.

## Frozen ReliabilityBench

Run a small local, resumable probe with jobs=1 at the case level, a 30-second
case timeout, one bounded retry, and atomic per-case JSON checkpoints:

1. inject a forecast-artifact failure immediately before sealing; verify the
   final ID is invisible, a diagnostic private partial remains, and a clean
   retry publishes a verified artifact;
2. repeat the same fault/retry for a JSON macro artifact;
3. synchronize two forecast-artifact writers at the seal boundary and require
   both calls to return the same verified final artifact;
4. synchronize two JSON-artifact writers at the seal boundary with the same
   requirement;
5. force an unexpected public MCP tool exception and require an `isError`
   result with typed `INTERNAL_ERROR`, not a JSON-RPC transport crash;
6. run twelve serial local public forecasts over the frozen short fixture,
   recording completion and p95 wall latency with no external/model calls.

The concurrency inside fixtures 3 and 4 is exactly two same-ID writers needed
to reproduce the production race; benchmark cases themselves remain serial.

## Frozen gates

- **Completion:** all six cases complete with no omitted denominator.
- **Fault isolation:** both injected failures leave no final artifact, identify
  a private partial tree, and their next clean call returns an integrity-sealed
  artifact readable through the public reader.
- **Same-ID concurrency:** 2/2 callers succeed for both artifact families,
  return one identical final path, and the winner passes every integrity hash.
- **Immutability:** the published forecast/JSON payload and integrity manifest
  match the single-writer control; first-write-wins never rewrites a winner.
- **Typed failure:** the forced unexpected MCP exception is a tool result with
  `INTERNAL_ERROR`, repair options, and no server/transport failure.
- **Representative load:** 12/12 serial forecasts complete, p95 wall latency is
  at most 1.0 second on the frozen local fixture, external calls and retries are
  zero, and every returned artifact verifies.
- **Topology:** case jobs=1, two writers only in the named race fixtures,
  30-second timeout, one retry, atomic checkpoints, and resumable identity.

## Stop rules

Promote only if every gate passes twice from a clean output root and the full
local suite remains green. If the baseline race cannot be reproduced, record a
validated no-build rather than changing publication code. If a fix requires a
global lock, daemon, unbounded wait, or deletion of ambiguous temporary trees,
stop and retain the current first-write-wins behavior.
